## Where the Spec Is Unclear

- **Which judge type to use.** The docs say an `llm_judge` is one call with no tools. This rubric must read the individual `step.&lt;id&gt;` spans, so I made the main file an `agent_judge`. The literal `llm_judge` version is there too.
- **How the quality rule names a detection.** The spec does not say whether `conditions[].detection` holds the display name, the slug or the UUID. I used the display name. A wrong value returns 404 "Detection not found", so a wrong guess fails at once. `PLAN.md` gives the slugs to try next, and a fallback of two ID-based threshold rules.
- **Form option keys.** The spec gives no keys for multiple-choice options. I guessed `{"choices": [...]}`. `PLAN.md` adds a `form get` check to confirm the choices saved before the cohort steps.
- **Model choice.** I left `modelProvider` and `modelName` empty, so the server default runs, because neither the docs nor the spec lists a valid value. `answerType` in the evaluator output fields has no listed values either, so I left it out and used `scoreType`.
- **What `cost` measures.** The spec does not say whether `cost` is per trace or per span. The rule also cannot be limited to the `firstrun` workflow.
- **First day of the cost alert.** The 24-hour window still holds today's runs from before the cap, so the cost alert fires once on day one.

## What the API Cannot Do

- **Score many traces in one call.** An evaluator run takes one `traceId`, with no filter, tag or workflow. `PLAN.md` loops over the 34 trace IDs.
- **Recurring AI scoring.** The API cannot attach an AI evaluator to an evaluation, and form replacement is limited to human questions. Assigning the evaluator to a recurring evaluation must happen in the app. After that, `evals schedules update` can change the cadence from the CLI.
- **Notify the reviewer.** `evals launch --assign-me` sends no email or Slack message. The reviewer finds the items in the app.
